01 / OVERVIEW

One product, three process roles.

Learnloom is a hosted modular monolith. It ships as one Go binary, but runs as separate web, worker, and migration processes around a shared PostgreSQL core.

The shortest useful mental model

The web role records intent. PostgreSQL makes that intent durable. Workers turn it into immutable artifacts. The web role later reads the durable projection and artifacts back to learners.

02 / PRINCIPLES

Why the architecture has this shape.

The apparent complexity is mostly deliberate containment: each difficult concern has one owner, and cross-cutting invariants live where they can be enforced consistently.

Postgres owns mutable truth

No worker-local queues or filesystem state decide what happens next. Scheduling, claims, attempts, quotas, retries, receipts, and deletion all survive process loss.

Packages follow product responsibilities

The code is not split into generic controller/service/repository layers. source, dossier, execution, and failure are deep modules with meaningful behavior.

Generation and delivery are separate

An email retry never spends model tokens again. A generated Dossier and its delivery receipt have independent claims, attempt budgets, and terminal states.

Untrusted input is normalized once

All source URLs pass through one bounded, DNS-pinned acquisition path. Search results are candidates only; extracted snapshots become evidence.

Public state is a safe projection

Internal failure detail stays in attempt records and structured logs. Learner surfaces receive stable codes, safe messages, retryability, and incident IDs.

Artifacts are immutable

Dossier JSON, Markdown, and HTML are rendered together, checksummed, compressed, and written under opaque account/Issue/generation keys.

03 / RUNTIME

Same binary, different dependency graphs.

cmd/learnloom/main.go validates configuration per role and constructs only the providers that role needs. This keeps deployment simple while allowing independent scaling.

HTTP

web

Serves the React build, authenticated JSON control plane, public learner subdomains, Clerk webhook, and health/metrics surfaces.

  • Needs Postgres + S3 + Clerk
  • Does not call the model or Resend
  • HTTP :3000 by default
JOB

worker

Polls durable work, freezes evidence, runs the Dossier pipeline, stores artifacts, delivers email, and completes deletion work.

  • Needs Postgres + S3 + model + Resend
  • Optional SearXNG discovery
  • Metrics/readiness :9090
SQL

migrate

Serially applies SQL embedded in the Go binary and exits. Each migration is transactional and protected by a Postgres advisory lock.

  • Needs Postgres only
  • Runs before web and worker rollout
  • Schema mismatch fails readiness

05 / ISSUE LIFECYCLE

An Issue is the durable unit of learning work.

A Newsletter describes recurring intent. An Issue is one scheduled or manual attempt to produce a Dossier from that intent.

scheduled intent→ queued→ generating→ generated→ delivery pending→ delivered

Generation failure

generating↘failed

Retryable failures return to queued with exponential backoff until the attempt budget is exhausted.

Delivery failure

delivering↘failed

Delivery can retry independently. Explicit user action can move a failed receipt back to pending.

Ambiguous delivery

delivering↘unknown

Never automatically replayed: the provider may have accepted the request before the claim was lost.

A
Artifact first, database second

The worker writes and checksums the artifact before CompleteIssue atomically records generated state, history, and a pending delivery receipt.

D
Delivery is not part of generation

Its own claim token, lease, attempt count, external ID, and status isolate provider ambiguity from expensive model work.

06 / SOURCES

Search discovers candidates. Snapshots become evidence.

The source module is a security boundary and an evidence engine. It resolves learner-provided or discovered URLs through the same safe path, then freezes the exact ordered evidence set on the Issue.

03

Check sufficiency

At least 4 usable items or one substantial exact article by default.

05

Discover if needed

SearXNG queries only when policy permits and catalog evidence is short.

06

Resolve candidates

Snippets are discarded as evidence; bounded top candidates use native fetch.

07

Rank + dedupe

Stable selection by usability, title/URL identity, recency, and max item count.

08

Freeze on Issue

provided

Use only the learner’s catalog. Insufficient evidence fails without autonomous search.

discovered

Autonomous search can fill the catalog. Generation requires the hard evidence minimum.

hybrid

Start with provided sources; search only to close a gap. A sufficient existing catalog can survive search outage.

SSRF and acquisition controls

  • Only HTTP and HTTPS; no URL credentials
  • Reject localhost, private, reserved, link-local, multicast, and documentation ranges
  • Resolve DNS first and pin the connection to a validated public IP
  • Revalidate every redirect; cap redirect count
  • TLS 1.2 minimum and bounded connection/header timeouts
  • Content-type allowlists for feeds and articles
  • Strict feed/article byte limits and character budgets
  • Conditional requests with ETag and Last-Modified
07 / DOSSIER PIPELINE

A small editorial room, encoded as stages.

The generator is not one giant prompt. It progressively narrows evidence, plans teaching, checks claims, writes, tests recall, edits, and runs a deterministic quality gate.

Model stages · purple = structured contract · blue = text · amber = optional parallel · green = deterministic gate
01 · CHECKPOINT

Curator

Selects evidence IDs and a coherent theme. JSON contract is validated against available sources.

02 · CHECKPOINT

Blueprint

Defines objective, prerequisites, mechanism, example, misconception, experiment, and continuity.

03 · CHECKPOINT

Researcher

Builds a source-grounded research brief within the intermediate context budget.

04 · CHECKPOINT

Skeptic

Challenges weak claims, missing nuance, evidence fit, and misleading simplifications.

05 · CHECKPOINT

Teacher

Writes the lesson for learner level, goal, history, citations, and time budget.

06 · PARALLEL

Examiner

Produces practice and numbered answers from the source-grounded lesson.

07 · OPTIONAL

Exploration

Runs beside Examiner when AI exploration is enabled.

08 · REPAIRABLE

Editor

Returns lesson, critique, practice, exploration, and notes under a strict JSON contract.

09 · deterministic, no model judgmentQuality gate → render JSON + Markdown + HTML → Learning History projectionChecks required sections, citation IDs, answer keys, blueprint coverage, history continuity, exploration contract, and lesson time-fit.

Structured stages get one repair attempt

Curator, Blueprint, and Editor outputs are decoded with unknown JSON fields rejected, then validated. A failed contract is summarized into a safe repair instruction and tried once more; repeated drift becomes a classified, retryable content-quality failure.

Reuse requires an exact fingerprint

The fingerprint incorporates pipeline version, model name, Newsletter learning settings, recent Learning History, and frozen Issue evidence. A restored structured checkpoint is validated again against today’s contract. Successful completion deletes the Issue’s checkpoints.

Validated work is preserved when the editor regresses it

If the editor damages an otherwise valid teacher lesson or examiner answer key, the generator can keep the independently validated outputs. Editor candidates that fail the current contract are never checkpointed.

Each stage receives weighted, bounded context

Sources and intermediate material are rune-limited and assembled with per-section weights. The required practice draft is protected in editor input; source candidate and article allocations adapt to item count.

What is transactional?

  • Claim selection + Issue transition + attempt creation
  • Generated state + history append + checkpoint cleanup + delivery enqueue
  • Newsletter scheduling advance + scheduled Issue creation
  • Migration SQL + schema version record

What is intentionally not one transaction?

  • S3 artifact write happens before DB completion
  • Provider delivery happens outside Postgres, under a lease
  • Database account deletion and bucket object deletion are independently observable
  • Search and source fetch occur outside DB transactions
09 / RELIABILITY

Leases make horizontal workers boring.

Workers coordinate using time-bounded database claims. Ownership is proven by a UUID token on every renewal, stage record, release, completion, or failure transition.

Fair claim selection

1
Check global pause + daily quota

A durable runtime switch can stop new model claims without redeploying.

2
Compute Account activity

Respect active generation and daily limits per Account.

3
Choose one candidate per Account

Oldest eligible work per Account, then Accounts with the oldest last-start time.

4
FOR UPDATE SKIP LOCKED

Concurrent workers skip rows already claimed by peers.

Lease behavior

Renewal
A companion goroutine extends the Issue or Delivery lease while work runs. Renewal also updates the append-only Issue attempt heartbeat.
Retry
Classified retryable failures return to the queue with bounded exponential backoff: 15s × 2^(attempt−1), capped at 15 minutes.
Claim loss
Expired Issue claims become abandoned evidence and are recovered separately. Infrastructure claim loss has its own bounded count and does not spend a generation attempt.
Graceful drain
A draining worker becomes unready and stops new claims, but keeps renewing current work. At deadline it releases active claims back to the queue without consuming content attempts.
!
Exactly-once external delivery is impossible here

Learnloom instead uses deterministic Resend idempotency keys and an explicit unknown outcome. If network failure makes acceptance ambiguous, automatic replay is less safe than surfacing uncertainty.

10 / SECURITY

Trust is narrowed at every boundary.

Security here is structural: hostname, identity, ownership, browser mutation, remote content, model output, public rendering, secrets, and provider errors each have a dedicated choke point.

HOST

Tenant routing

Strict root/app/username classification; malformed and unknown hosts receive 421.

AUTH

Identity

Verified Clerk subject and session ID create server-side Account context.

SCOPE

Ownership

Every control-plane store query carries the current Account ID.

BROWSER

Mutations

Exact Origin + HMAC CSRF + JSON content type + bounded request body.

FETCH

Remote sources

Public-IP validation, DNS pinning, redirect checks, time and size bounds.

MODEL

Generated content

Strict contracts, escaped rendering, known citation IDs, deterministic quality checks.

PUBLIC

Reading pages

Public-only projections, canonical paths, restrictive CSP, escaped metadata.

ERROR

Failure privacy

Safe public messages are separated from internal diagnostic detail and incident IDs.

CONFIG

Secrets

Environment-only configuration; production TLS validation; provider keys redacted from errors.

12 / OPERATIONS

Production behavior is part of the architecture.

The system is designed for immutable image rollout, forward-only migrations, independently scaled workers, dependency-aware readiness, and recovery of interrupted leases.

Deployment order

1
Provision Postgres + private S3

They form the documented recovery set.

2
Configure identity + providers

Clerk domains/webhook, model endpoint, Resend sender, optional SearXNG.

3
Run migrate once

Only then roll web and worker images.

4
Verify health, readiness, metrics

Shift DNS/TLS traffic after dependencies and schema are current.

Signals that matter

  • Readiness and HTTP 5xx / rate-limit spikes
  • Oldest queued Issue age and exhausted attempts
  • Active Issues, draining state, recovered/released claims
  • Stage/model latency, provider errors, renewal failures
  • Delivery failure rate and unknown outcomes
  • Postgres pool saturation and S3 errors
  • Browser web vitals logged through the control plane

Backup

Postgres PITR + S3 versioning/encryption; test isolated restores quarterly.

Rollback

Roll app images back; never reverse a database migration in place. Keep schema compatible through rollout.

Pause

A durable generation control stops new model claims; scale workers to zero to stop scheduling and delivery.
